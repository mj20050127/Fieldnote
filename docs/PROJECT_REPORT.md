# 基于 MongoDB 的在线问卷系统项目完成报告

项目名称：拾问 Fieldnote　　阶段：第一阶段　　报告日期：2026 年 10 月 19 日

## 一、项目目标

本项目依据《大作业一第一阶段》实现一个简化的在线问卷系统。注册用户能够创建问卷、配置题目和跳转规则、发布分享链接，并查看自己问卷的答卷及统计；填写者登录后按实际路径作答，系统校验答案并保存每一次成功提交。

项目使用 MongoDB 保存全部业务数据，不使用关系型数据库，也未使用现成问卷系统框架。设计重点是按访问方式组织数据、把条件规则保存为配置、保证并发提交的一致性，并为第二阶段在原系统上扩展保留基础。

第一阶段已实现注册登录、问卷管理、单选和多选、文本及数字填空、条件跳转、填写校验、匿名与重复填写策略、整卷和单题统计。公网服务器部署不属于已完成结果；当前交付包含本地运行方案和待实际验收的部署配置。

## 二、系统设计

### 2.1 技术架构

系统采用浏览器前端、HTTP API 和 MongoDB 三部分结构。Vue 3、TypeScript、Vite 和 Element Plus 实现页面；FastAPI 处理接口与权限，Pydantic 约束数据结构，PyMongo Async 访问 MongoDB。前端不直接访问数据库，业务校验由后端最终执行。

| 层次 | 主要职责 | 实现位置 |
|---|---|---|
| 页面与交互 | 登录、工作台、编辑、填写、统计 | frontend/src/pages/ |
| API 与认证 | 接口、会话、CSRF、所有权过滤 | backend/app/main.py、auth.py |
| 业务与规则 | 发布、提交、校验、路径重放 | services.py、logic.py |
| 数据访问 | 集合约束、索引、读取与统计聚合 | database.py、repositories.py |

### 2.2 业务流程与权限

创建者登录后创建草稿，添加题目、选项、校验条件及跳转规则。保存后执行发布检查，通过后发布并获得 /survey/{public_code} 链接。填写者登录后逐题回答，后端决定下一题；提交时重新计算完整路径，成功后写入一份答卷。创建者通过受所有权限制的接口读取统计与原始答卷。

问卷状态为 draft、published、closed；expired 根据已发布状态和当前截止时间计算。发布后冻结题目与填写设置，允许调整截止时间或关闭问卷。匿名表示向创建者隐藏填写账号，填写者仍需登录，服务端保留账号关联以执行重复填写限制。

## 三、MongoDB 设计

### 3.1 集合划分与字段

实际 MongoDB Schema 位于 backend/app/database.py，由 initialize_database 在应用启动时创建或更新集合验证规则与索引。Pydantic 请求、响应模型位于 backend/app/schemas.py，两者分别承担数据库结构约束与接口数据约束。

| 集合 | 关键字段及类型 | 用途 |
|---|---|---|
| users | _id、username、username_key、password_hash：字符串；created_at：日期 | 账号、规范化用户名和密码哈希 |
| surveys | _id、owner_id、public_code、title、description、status：字符串；settings：对象；questions：数组；deadline：日期或 null | 问卷定义、题目、规则和生命周期 |
| responses | survey_id、respondent_id、request_id、payload_hash：字符串；answers、visited_question_ids：数组；submitted_at：日期 | 每次成功填写的答案及实际路径 |
| sessions | _id、user_id、csrf_token：字符串；created_at、expires_at：日期 | 服务端会话与过期控制 |

主键使用 UUID 字符串；关联字段为应用引用，由后端检查对象存在性、所有权和引用有效性。MongoDB 不提供这些字段的外键约束。密码保存 Argon2 哈希，会话令牌以 SHA-256 哈希作为数据库主键。

### 3.2 嵌入、引用与冗余取舍

题目、选项、校验配置和跳转规则一起读取且数量有界，因此嵌入 surveys.questions。答卷持续增长，独立保存，避免无界数组。账号和会话有独立生命周期，分别保存为集合。

关系型数据库同样可以实现问卷。本项目按 MongoDB 嵌套文档和单文档原子写入方式建模，没有把关系表机械翻译为集合。不同题型通过 validation、routing 保存差异，单份答卷一次完整插入。

不冗余保存累计答卷数和平均值，查询时从答卷聚合生成。单选答案保存选项 ID，多选答案保存去重排序后的 ID 数组；访问路径与有效答案分开保存，用于区分跳过题、留空题和实际回答。

### 3.3 结构验证与版本字段

数据库使用 $jsonSchema 检查必填字段、BSON 类型、题型枚举和数组结构；例如题目最多 100 道，每题最多 50 个选项和 20 条规则。应用负责跨字段范围、选项引用、跳转目标与权限等业务约束。数据库结构校验不能代替应用层业务校验。

schema_version 表示存储结构版本，definition_version 表示答卷对应的问卷定义版本，revision 表示并发修改版本。第一阶段定义版本为 1；发布后定义固定，避免历史答卷对应的题目含义变化。

### 3.4 索引与一致性

| 索引 | 类型或条件 | 作用 |
|---|---|---|
| users.username_key | 唯一 | 防止并发注册同名账号 |
| surveys.public_code | 唯一 | 通过分享码定位问卷 |
| surveys(owner_id, created_at DESC) | 复合 | 自己的问卷列表及排序 |
| responses(survey_id, submitted_at DESC) | 复合 | 答卷分页及统计前过滤 |
| responses(survey_id, respondent_id, request_id) | 唯一 | 同一提交请求重试不新增答卷 |
| responses(survey_id, respondent_id) | 条件唯一；single_submission=true | 不允许重复时，每账号最多一份 |
| sessions.expires_at | TTL | 清理过期会话；请求时仍主动检查过期 |

草稿保存以 _id、owner_id、revision 和 draft 状态共同过滤，成功后 revision 加 1；旧版本请求返回 409，避免两个窗口互相覆盖。截止时间修改也采用版本控制，前端只合并管理元数据，保留未保存的本地定义。

提交携带 request_id，服务端计算规范化内容摘要。相同编号、相同内容返回原回执；相同编号但不同内容返回冲突。成功请求的重试检查先于关闭、截止和禁止重复检查。允许主动重复填写时，新填写使用新编号；唯一索引处理并发竞争。

### 3.5 统计设计与实际示例

整卷统计先按 survey_id 过滤，再通过 $facet 并行计算总数、到达数、有效回答数、数字平均值及选择题次数。实现位于 repositories.py；下列为数字平均值分支的核心形式：

~~~json
[
  {"$match": {"survey_id": "survey-id"}},
  {"$unwind": "$answers"},
  {"$group": {
    "_id": "$answers.question_id",
    "count": {"$sum": 1},
    "average": {"$avg": "$answers.value"}
  }}
]
~~~

完整实现对选择题分别按题目 ID 和选项 ID 分组，多选再展开答案数组，并根据定义补回次数为 0 的选项。单题接口另外分页返回文本和数字原始值，避免一次返回全部内容。

固定三份测试答卷中，单选 A/B/A 的 A、B、C 次数为 2、1、0；多选 XY/Y/XZ 的 X、Y、Z 次数为 2、2、1；数字 10、20、留空的有效回答数为 2，平均值为 15，无人回答时为 null。多选比例以该题有效回答数为分母，总和可以大于 100%。

## 四、跳转设计

### 4.1 规则结构

每道题保存 routing.rules 和 default_target。每条规则由 operator、value、target 组成，条件针对当前题答案。规则数组顺序就是优先级，第一条匹配规则生效；未匹配走默认目标。NEXT 表示下一题，END 表示结束。第一阶段仅允许向后跳转，发布检查拒绝不存在或位于当前题之前的目标。

| 题型 | 支持的条件 | 示例 |
|---|---|---|
| 单选 | eq | 选择 no 后跳到 reason |
| 多选 | contains_any、contains_all | 包含 match 后跳到 suggestions |
| 数字 | eq、gt、gte、lt、lte | 每周次数大于等于 3 后跳到 activities |
| 文本 | 默认流转 | 按 NEXT、指定后续题目或 END 继续 |

下面的配置保存在问卷文档中，业务代码按统一运算符解释执行，不为某份问卷写专用分支，也不使用 eval 执行配置：

~~~json
{
  "id": "sessions",
  "type": "number",
  "routing": {
    "rules": [
      {"operator": "gte", "value": 3, "target": "activities"}
    ],
    "default_target": "suggestions"
  }
}
~~~

### 4.2 实际填写路径

足球示例中，首题选择“不参加”时，路径为 participate、reason、other；选择“参加”、次数为 2 时，路径为 participate、sessions、suggestions、other；次数为 3 且活动选择 training 时，路径为 participate、sessions、activities、other。各路径仅校验实际到达的必答题。

### 4.3 防止伪造路径

下一步接口接收当前题和此前答案，从首题重新计算访问顺序，不信任客户端声明的进度。最终提交再重放完整路径，拒绝未知题目、重复题目、夹带跳过题的答案以及伪造的当前题。前端返回修改历史答案时，会清除旧分支后续答案。

预览、下一步与提交共用 logic.py 的规则引擎，预览不写答卷。发布检查可以识别结构上不可达的题目并提示警告，但不声称穷举所有条件组合的可达性。

## 五、校验设计

### 5.1 答案与配置校验

前端提供输入控件、长度提示和错误反馈，后端承担最终校验。客户端绕过页面直接发送请求，也必须经过相同的问卷定义和路径检查。

| 对象 | 主要校验 | 失败处理 |
|---|---|---|
| 必答题 | 实际到达后不能留空；数字 0 不是空值 | 指明题目并拒绝继续或提交 |
| 单选 | 必须为已有选项 ID | 拒绝未知选项或错误类型 |
| 多选 | 选项有效、不重复，满足最少与最多数量 | 拒绝越界；两项限制都为 2 即必须选 2 项 |
| 文本 | 去首尾空白，按 Unicode 码点检查长度 | 拒绝过短、过长及必答空白 |
| 数字 | 有限数值、上下界、整数要求；绝对值不超过 2^53-1 | 拒绝字符串、布尔值、NaN、无穷等 |
| 发布配置 | 题干、选项、ID、范围、规则类型和目标有效 | 检查返回 errors、warnings，非法定义不可发布 |
| 可作答性 | 必答文本不能最多 0 字；整数区间至少有一个有效整数 | 阻止配置合法但无法作答的问卷发布 |
| 生命周期 | 必须已发布且未关闭、未截止；定义版本一致 | 状态或版本冲突返回 409 |

可选题留空按 None 处理，不保存为空的答案，但记录访问路径。可选文本最多 0 字仍允许留空。整数区间检查包含端点，并与安全整数域求交集；0.1 至 0.9 的整数题拒绝发布，0.1 至 1 的整数题允许填写 1。未要求整数时，前一区间允许填写 0.5。

### 5.2 账号、权限和请求校验

注册和登录使用密码哈希及服务端会话，Cookie 设置 HttpOnly、SameSite=Lax，生产环境启用 Secure。写请求检查 CSRF，提供 Origin 时验证来源。管理接口按 owner_id 过滤，其他账号不能访问或修改问卷及答卷；匿名答卷通过字段白名单隐藏填写账号。

请求体限制为 1 MiB，输入模型拒绝额外字段。常见响应为未登录 401、CSRF 或来源错误 403、资源不可访问 404、版本或状态冲突 409、输入不合法 422、请求过大 413。注册和登录使用单进程限流，未来多实例部署需改为共享限流状态。

## 六、AI 使用过程

### 6.1 工具、真实提示与生成内容

前期使用 GPT 形成设计方案，随后使用 Codex 辅助分析作业、实现和修复程序、编写测试及文档。配套工具包括 PowerShell、Python、npm、pytest、Playwright，以及 MongoDB 官方文档和公开项目资料。初始方案保留在 docs/gpt_log.md，过程记录在 docs/AI_LOG.md。

### 6.2 AI 结果的修改与核验

AI 生成代码后出现过前端类型错误、浏览器与 Python 的字符计数差异，以及两处业务边界缺陷。Unicode 字数改为按码点计数；截止时间响应改为保留本地定义并合并管理元数据；发布检查新增必答文本和整数范围可作答性判断。上述修改通过针对性回归和完整测试验证。

例如修改发布检查前，新增的 7 项非法配置回归全部失败；修复后通过。修改截止时间逻辑前，浏览器回归捕获新标题被恢复为旧值；修复后验证设置、取消、保存和版本冲突场景通过。这表明“AI 已生成代码”不能直接作为功能正确的依据。

### 6.3 开发者与 AI 的工作边界

开发者提供原始方案和作业文档，决定先完成提交与答辩期间的演示目标，授权实施，并通过字号、留白和需求复核等反馈推进调整。实现、测试执行和本次缺陷修复由 AI 辅助完成，不将其虚构为学生手写代码或独立提出的算法。设计取舍和最终采纳的实现已在本报告及源代码中展开，便于检查和答辩说明。

## 八、遇到的问题

开发中主要遇到七类问题：并发提交可能重复落库；两窗口保存可能覆盖；客户端能够伪造填写路径；匿名与登录要求容易混淆；浏览器与 Python 对 emoji 的长度计算不一致；截止时间更新覆盖未保存草稿；只比较上下界仍会放行没有合法答案的配置。此外，初次构建还暴露过类型契约和浏览器依赖匹配问题。

这些问题说明，页面能够操作并不代表数据一致性和边界行为已经正确。需要将问题转换为可重复的输入，明确数据库约束与应用校验的分工，并用测试保留修复证据。

## 九、问题解决与后续演进

### 9.1 解决措施与验证依据

| 问题 | 采用的解决措施 | 验证依据 |
|---|---|---|
| 并发重复与请求重试 | 唯一、条件唯一索引；规范化摘要；重试优先查原回执 | 并发和幂等 API 用例，保存份数符合策略 |
| 草稿并发覆盖 | 保存、发布及管理更新检查 revision | 旧版本返回 409，数据不被覆盖 |
| 伪造路径和跳过必答 | 预览、下一步和提交共用规则引擎；服务端从首题重放 | 未知、重复、路径外答案被拒；合法跳过可提交 |
| 匿名与免登录混淆 | 填写必须登录；对创建者的输出隐藏账号字段 | 匿名列表和详情测试通过 |
| Unicode 长度不同 | 前后端统一按码点计数，后端最终校验 | “你 + U+1F642 表情”在两码点限制下成功提交 |
| 截止时间丢失编辑 | 只合并管理元数据及新版本，保留本地定义与未保存状态 | 设置、取消、保存刷新及冲突回归通过 |
| 无法作答仍可发布 | 必答文本允许非空；整数区间与安全整数域存在交集整数 | 非法配置阻止发布，合法端点和小数用例通过 |

### 9.2 第一阶段边界

当前只支持当前题条件和向后跳转，发布后不编辑定义，不保存填写中的草稿。提交在最终读取状态时仍开放即视为已受理，可能在随后关闭后完成插入；系统没有承诺跨集合的严格关闭线性化语义。限流状态目前属于单进程，扩为多实例时需要共享状态。
