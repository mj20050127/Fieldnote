建议第一阶段采用 Python + FastAPI + PyMongo + MongoDB + 简单 HTML/JavaScript 页面，做出一个功能完整、便于第二阶段扩展的问卷系统。

根据 大作业一第一阶段.docx，MongoDB 设计占 35 分，后端逻辑占 25 分，第二阶段还要求在第一阶段代码上继续修改。因此，你应该把主要精力放在数据结构、跳转规则、校验和测试上，前端做到清楚、能操作即可。

下面这套方案可以直接作为你的开发依据。

先确定第一阶段要完成的功能，以及需求中没有明确说明的行为。
模块	第一阶段实现内容
用户账号	注册、登录，密码加密存储
问卷管理	创建问卷、编辑草稿、查看自己的问卷、发布、设置截止时间、关闭

文档有几个需要你自行明确的地方，我建议采用以下约定，并写进项目报告：
- 匿名仍然需要登录：匿名表示向问卷创建者隐藏填写者身份。后台保留账号关联，用于判断是否重复提交。这个方案实现的是“对创建者匿名”。
- 允许匿名时，由填写者选择是否匿名；不允许时按实名账号提交。
- 允许重复时，每次主动提交都保存为一份新答卷；网络重试不重复保存。
- 被跳转跳过的题目不要求作答，即使该题设置了必答。
- 第一阶段只允许向后跳转或结束问卷，避免循环。
- 发布后固定题目、选项、跳转规则、匿名和重复提交设置；截止时间和关闭状态仍可管理。这样可以保证旧答卷的含义不会随编辑而改变。
这些属于建议的设计决策，不是文档逐项规定的规则。

技术上，采用前后端放在同一个项目中的简单结构。
部分	建议选择	作用
后端	FastAPI	提供接口、登录校验和业务逻辑
数据库访问	PyMongo	直接操作 MongoDB，便于展示数据库设计
请求模型	Pydantic	检查接口参数的基本类型
登录认证	JWT + 密码哈希	验证登录身份
前端	HTML、CSS、JavaScript	实现编辑器、填写页和统计页
测试	pytest + API 测试	验证核心逻辑和接口
运行环境	本地或 Ubuntu，MongoDB 可用 Docker 启动	方便复现和提交


密码应存储哈希值，建议使用 Argon2；FastAPI 官方教程提供了密码哈希与 JWT 的实现方式。FastAPI

后端建议按职责拆分，至少区分：
- routers：处理请求和返回结果。
- services：问卷管理、提交、统计等业务逻辑。
- repositories：MongoDB 查询与写入。
- schemas：请求和返回的数据模型。
- logic：跳转规则与答案校验。
其中，跳转引擎和校验器要写成独立函数。这样第二阶段增加规则或题型时，可以继续扩展现有代码。

数据库建议使用三个核心集合，题目嵌入问卷，答卷单独保存。
集合	主要字段	存储内容
users	_id、username、password_hash、created_at	用户账号
surveys	_id、owner_id、public_code、title、description、status、deadline、settings、definition_version、questions、创建和更新时间	问卷定义及全部题目
responses	_id、survey_id、definition_version、respondent_id、is_anonymous、answers、visited_question_ids、request_id、single_submission、submitted_at	每次成功提交的完整答卷


这里最重要的设计是：

一份问卷中的题目数量相对有限，填写时通常需要一起读取，因此放进 surveys.questions 数组。 题目的选项、校验条件、跳转规则继续嵌入对应题目。

答卷数量会持续增长，因此一份答卷保存成一个独立的 responses 文档。 不把全部答卷塞进问卷文档，避免文档持续膨胀，也方便多人同时提交。MongoDB 的嵌入模型适合一起读取的数据，但单个文档有 16 MiB 大小限制。MongoDB Docs

报告中可以这样解释选型：关系型数据库同样能够实现问卷系统；本项目使用 MongoDB，既符合课程要求，也能通过嵌套文档自然表达不同题型及其配置。

建议至少建立这些索引：
索引	用途
users.username 唯一索引	防止重复注册，用户名先统一规范化
surveys.public_code 唯一索引	根据分享链接定位问卷
surveys(owner_id, created_at)	查询自己的问卷列表
responses(survey_id, submitted_at)	查询答卷和统计数据
responses(survey_id, respondent_id, request_id) 唯一索引	防止同一次提交因重试而重复保存
responses(survey_id, respondent_id) 条件唯一索引	对不允许重复填写的问卷限制每账号一份答卷


最后一个索引只约束 single_submission: true 的答卷。这个字段必须由后端根据问卷设置生成，并且发布后固定重复提交策略。MongoDB 支持将唯一约束应用于满足条件的部分文档。MongoDB Docs

题目使用统一的外层结构，题型差异放进配置字段。

文档中的三类题目，可以在程序中拆成四种类型：
single_choice
multiple_choice
text
number

例如，一道数字题可以设计为：
{
  "id": "q_sessions",
  "type": "number",
  "title": "你每周踢球多少次？",
  "order": 2,
  "required": true,
  "validation": {
    "min_value": 0,
    "max_value": 14,
    "integer_only": true
  },
  "routing": {
    "rules": [
      {
        "priority": 1,
        "operator": "gte",
        "value": 3,
        "target_question_id": "q_activities"
      }
    ],
    "default_target": "q_suggestions"
  }
}

单选和多选题再增加 options 数组：
[
  {"id": "training", "text": "日常训练"},
  {"id": "match", "text": "参加比赛"}
]

注意，题目和选项都使用稳定 ID，显示顺序另用 order 表示。跳转和答卷引用 ID，不引用“第几题”或选项文字。这样调整顺序、修改文字时，关联关系仍然清楚。

一份答卷的 answers 可以统一保存为：
[
  {"question_id": "q_participate", "value": "yes"},
  {"question_id": "q_sessions", "value": 4},
  {"question_id": "q_activities", "value": ["training", "match"]},
  {"question_id": "q_suggestions", "value": "希望增加每周训练次数"}
]

单选存选项 ID，多选存 ID 数组，文本存字符串，数字存数值。

跳转规则应该存为数据，由统一引擎执行。

第一阶段支持以下条件就足以覆盖要求：
题型	条件	示例
单选	eq	选择“参加”后跳到指定题目
多选	contains_any	包含指定选项中的任意一个
多选	contains_all	同时包含指定的全部选项
数字	gt、gte、lt、lte、eq	次数大于等于 3 时跳转


执行规则统一为：
1. 当前答案通过校验。
2. 按 priority 从小到大检查条件。
3. 使用第一条命中的规则。
4. 没有命中则执行默认跳转；默认也可以配置为下一题。
5. 目标为 END 时进入提交步骤。
不要把问卷条件转换成代码后执行，使用固定的运算符列表逐项判断即可。

发布前还要检查规则本身是否合法：目标题目存在、条件与题型匹配、引用的选项存在、目标位于当前题之后，以及最后能够到达结束位置。

前端可以展示跳转过程，但后端提交时必须重新计算完整路径。否则，用户直接调用接口，就可能绕过前端的必答和跳转限制。

答案校验分成基本结构校验和问卷业务校验。

Pydantic 检查请求格式；你自己编写的校验器根据题目配置检查具体答案。
类型	校验规则
单选	必答时不能为空；选项 ID 必须存在
多选	选项必须存在、不能重复；检查最少和最多选择数
文本	必答检查；检查最短和最长长度
数字	必须为有限数值；检查上下界及整数要求
整份答卷	拒绝重复题目 ID、未知题目 ID、路径之外的答案


“必须选择 2 个”可以表示成 min_choices = max_choices = 2。

有三个细节需要特别处理：
- 可选题允许留空；一旦填写，就要满足该题的限制。
- 数字 0 是合法答案，不能用简单的真假判断把它当作未填写。
- 必答检查只针对实际经过的题目。
前端负责及时提示，后端负责最终判定。同时在 MongoDB 初始化脚本中设置基础 schema validation，约束必要字段、数据类型和状态枚举。

提交时，从第一题重新推演路径，成功后一次保存整份答卷。

建议处理顺序为：
1. 验证登录，确认问卷已经发布且未关闭、未截止。
2. 从登录信息取得账号 ID，不接受客户端指定填写者身份。
3. 从第一题开始，逐题验证答案并计算下一题。
4. 到达结束位置后，检查是否夹带了路径之外的答案。
5. 根据问卷设置生成匿名、重复提交控制字段。
6. 将整份答卷写入一个 responses 文档。
7. 返回答卷编号和提交时间。
如果允许返回上一题，修改前面的答案后，前端应清除后续旧路径的答案，再重新跳转。

每个填写页面生成一个 request_id：同一次提交重试沿用它，主动“再填一次”才生成新的值。这样既支持重复填写，也能避免双击提交导致重复计数。

统计直接从已提交答卷生成，第一阶段采用实时聚合即可。
题型	返回结果
单选	各选项选择次数、有效回答份数
多选	各选项被选择次数、有效回答份数
文本	分页查看全部有效填写内容
数字	有效回答数量、填写内容、平均值


实现时先按 survey_id 筛选，再展开答案数组进行分组、计数或求平均。

需要明确统计口径：
- 允许重复填写时，默认按答卷份数统计。
- 跳过或未填写的答案不参与数字平均值。
- 多选题的选项次数之和可以超过答卷数。
- 没人选择的选项也返回 0。
- 没有有效数字答案时，平均值返回空值，而不是 0。
所有管理、答卷查看和统计接口都必须验证 owner_id。匿名答卷的返回结果中隐藏账号关联字段。

前端做五个页面即可：登录注册、我的问卷、问卷编辑器、问卷填写、结果统计。

编辑器中的每道题使用一个配置区域，提供题型、题干、必答、选项、校验限制和跳转设置。填写页一次显示一道题，便于体现跳转行为。分享链接使用 /survey/{public_code}，未登录时先登录，再返回原问卷。

演示问卷可以选择你比较熟悉的足球活动场景。

题目	类型及限制	跳转
